## Context

GTC Mongolia sells package tours from Ulaanbaatar to China, Thailand, Vietnam, Turkey and beyond.
The public site — tours, destinations, flight tickets, travel insurance — is the front of a much
larger system. Behind it, managers price tours, issue contracts and invoices, chat with customers
and track their tasks, and agents earn commission through promo codes.

## What I built

Two of us built the system. By git authorship I wrote about 980 of its roughly 1,270 commits.
{/* src: git shortlog over the four author identities */}

- **The data layer.** The backend moved from raw SQL to Prisma and then to Drizzle on PostgreSQL;
  I wrote the query layer that let it do so without rewriting the routes.
- **Authentication** with Better Auth: email and password, Google sign-in, required email
  verification.
- **The production server** for the React app: security headers, and server-rendered titles and
  link previews for tour and news pages.
- **Contract signing**, from template to signed PDF.
- **Travel insurance:** quotes and purchase through daatguul.mn.
- **HiPay invoicing** and the fix for race conditions in pay-first QPay orders.
- **The customer AI chat assistant**, the real-time chat between staff and customers, and the
  Expo mobile app with push notifications.

My colleague ganaabna led the Golomt card-payment integration and the first versions of the
e-commerce, promo-code and commission features.

## Decisions

<Decision
  locale="en"
  title="One query API across three data layers"
  problem="Around 70 route modules had been written against the old data-access API. Each migration — raw SQL, then Prisma, then Drizzle — threatened a rewrite of all of them."
  tradeoff="A homemade abstraction of about 1,200 lines that the team has to maintain, with looser types at its boundary."
>
  A proxy (`queryClient.ts`) exposes Prisma-style calls on top of Drizzle: it maps camelCase to
  snake_case and raises Prisma's error codes (`P2002`, `P2025`), so existing routes and their error
  handling kept working unchanged.
</Decision>

<Decision
  locale="en"
  title="Deposit rules that can't drift"
  problem="The deposit a customer pays depends on how far away departure is. The rule runs in the browser, to show the price, and on the server, to charge it — and copies of it had already drifted apart once."
  tradeoff="The rule is still written twice, because the frontend and backend share no build step. Only the fixture is shared."
>
  Both implementations are tested against one JSON fixture, signed off by the product owner. The
  functions take no tour argument at all, so a per-tour exception can't be added quietly.
</Decision>

<Decision
  locale="en"
  title="Contracts signed without an account"
  problem="Customers sign a legally binding contract from a link a manager sends them, without logging in."
  tradeoff="The link is the credential, so expiry, rate limits and the audit trail have to do the work that authentication normally does."
>
  Templates are rendered and escaped on the server and sanitised again with DOMPurify in the
  browser. Signing links expire seven days after they're sent, every state change is appended to an
  audit log, and the public endpoints are rate-limited and validated with Zod.
</Decision>

<Decision
  locale="en"
  title="A server in front of a single-page app"
  problem="A React single-page app gives search engines and chat-app link previews an empty page, and static hosting offers no place to set security headers."
  tradeoff="One more Node process to run and monitor, instead of serving files from a CDN."
>
  An Express server serves the built app, sets HSTS, frame, referrer and permissions policies, and
  writes each tour's and news post's title and Open Graph tags into the HTML before sending it.
</Decision>
