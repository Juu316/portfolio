## Context

Shuren Goyol sells pearls, rings, necklaces, earrings, bracelets and watches, plus digital gift
cards. Shoppers can check out as guests, pay with QPay or a bank app through the Wire gateway,
follow their order and review what they bought. Staff run the shop from a separate admin portal:
products, stock, orders, gift cards, reports and the wording of the site itself.

## What I built

All of it, alone, in 72 commits between 24 August and 9 October 2026: the storefront (19 pages),
the admin portal (26 pages) and the shared TypeScript package that holds the business logic both
apps use. The two apps deploy as separate Cloudflare Workers bound to the same D1 database and R2
image bucket. The project's working name was Nova, and the Cloudflare resources still carry it.

## Decisions

<Decision
  locale="en"
  title="Stock as an append-only ledger"
  problem="Two shoppers buying the last necklace at the same moment must not both succeed, and every correction staff make has to stay traceable."
  tradeoff="Stock is a SUM over rows instead of a single column, and the history only grows."
>
  Stock is the sum of ledger rows. A sale appends a negative row with a single conditional `INSERT …
  SELECT … WHERE` that only writes if the total stays at zero or above, and D1 serialises writes, so
  nothing can slip between the check and the write. Corrections are new rows, never edits.
</Decision>

<Decision
  locale="en"
  title="The payment provider is the only source of truth"
  problem="News of a payment arrives four ways — the webhook, the return redirect, the order page polling, a cron sweep — and any of them can be late, repeated or forged."
  tradeoff="An extra API call for every confirmation. Money that arrives for a cancelled order is flagged for staff to refund by hand, not fixed automatically."
>
  All four paths call one function that re-reads the payment from Wire's API. The webhook's
  signature is checked, but its body is never trusted. Marking an order paid is a guarded `UPDATE …
  WHERE status = 'pending'`, so exactly one path wins and only the winner sends the confirmation
  email. Every request to Wire carries an idempotency key.
</Decision>

<Decision
  locale="en"
  title="A cron job inside a SvelteKit Worker"
  problem="Orders that are never paid must release their stock, and scheduled gift cards must go out on their date — but SvelteKit's Cloudflare adapter can't produce a scheduled handler."
  tradeoff="The wrapper depends on the shape of the adapter's output, so an adapter upgrade can break it."
>
  A small custom Worker entry wraps the generated one and adds a `scheduled` handler that runs every
  five minutes.
</Decision>

<Decision
  locale="en"
  title="A security review of my own code"
  problem="Staff upload product images, and an SVG is a document that can run script on the shop's own domain."
  tradeoff="Only raster images are accepted, so the brand's SVG artwork has to be exported first."
>
  A review I wrote up in the repo found that SVG uploads passed the check, along with other issues.
  Uploads now reject SVG, both image proxies send `nosniff` and a sandboxing CSP, and they serve
  only storage keys that match an allowlist.
</Decision>
